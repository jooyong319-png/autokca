# architecture — 라우트·데이터 흐름·규약

> 구조가 바뀌면 여기를 고친다([[SCHEMA]]). 코드와 다르면 코드가 맞다.

## 스택

Next.js 14 App Router · CSS 모듈 · TypeScript strict · Supabase(Postgres) · Vercel.
**의존성은 `next`·`react`·`react-dom` 셋뿐이다** — 나머지는 표준 API로 해결했다.

## 라우트

| 경로 | 렌더 | 역할 |
|---|---|---|
| `/` | ISR 60s | 피드. **scroll-snap 켜짐**(한 화면 = 한 질문) |
| `/q/[slug]` | SSG + `dynamicParams: true` | 질문 상세. **검색 착지 페이지.** 댓글 + 이어지는 피드. 스냅 꺼짐 |
| `/q` | ISR 1h | 질문 전체 목록 |
| `/c/[topic]` | SSG | 주제 허브 8개. 크롤 경로 + "돈 관련 투표 모음" 롱테일 |
| `/best` | ISR 30m | 집계 — 팽팽한/몰린/표 많은 질문 TOP 10 |
| `/me` | 정적 · **noindex** | 성향 확인서. 브라우저 기록만 씀 |
| `/about` `/terms` `/privacy` | 정적 | 법적 고지 |
| `/api/vote` | dynamic | `GET`=내 투표 상태 · `POST`=투표 |
| `/api/comments` | dynamic | `GET`=폴링 목록+tops+counts · `POST`=작성 · `[id]` `PATCH`=공감·신고 |
| `/api/feed` | dynamic | 무한 스크롤 다음 묶음 |
| `/api/stats` | ISR 5m | 누적 표 수(푸터) |
| `/opengraph-image` · `/q/[slug]/opengraph-image` | **dynamic** | 공유 카드 |

⚠️ **`dynamicParams`는 `true`여야 한다.** `false`면 질문을 추가해도 재배포 전까지 404가 난다.
범위 밖 슬러그는 `notFound()`가 막으므로 soft-404 위험은 없다.

⚠️ **OG 라우트는 `force-dynamic`이다.** 빌드 프리렌더를 시도하면 Windows에서
`@vercel/og`가 빌드 자체를 실패시킨다(통합 위키 `nextjs.md` 참고).

## 데이터 흐름

```
lib/questions.ts (질문 103개 · 코드에 박혀 있다)
        │
        ├─ feedOrder(exclude, votesOf) ── 진지 1 : 병맛 2, 각 갈래는 표 많은 순
        │
        ▼
서버 컴포넌트 ──▶ lib/votes.ts ──┐
                lib/comments.ts ─┤── lib/supabase.ts ──▶ PostgREST RPC
                                 │        (환경변수 없으면 전부 null)
                                 ▼
                          Supabase: tallies · comments
```

**질문은 DB에 없다.** 코드에 있다. DB에는 집계(`tallies`)와 댓글(`comments`)만 있다.
그래서 질문을 고치려면 배포해야 하고, 그게 "발행은 수동"([[SCHEMA]] 제2원칙)과 맞물린다.

### Supabase는 서버만 만진다

`service_role` 키로 PostgREST **RPC만** 호출한다. SDK를 넣지 않았다 — 하는 일이
"카운터 읽고 올리기 + 댓글 CRUD"뿐이라 의존성 값이 없다.

- **원자적 증가**를 DB 함수에 맡긴다. 읽고 나서 쓰면 동시 투표가 유실된다
- 브라우저는 DB를 직접 만지지 않는다. anon 키를 노출하지 않는다
- **환경변수가 없어도 사이트가 돌아간다** — 결과를 감추고 그 사실을 화면에 밝힌다
- ⚠️ **PostgREST `max-rows` 기본 1000.** `all_tallies`·`all_comment_counts`는 질문이
  1000개를 넘으면 조용히 잘린다. 그때는 페이지네이션이나 사전 계산이 필요하다

스키마는 `supabase/schema.sql`이 소스 오브 트루스다(사람이 SQL Editor에서 1회 실행).
`create or replace`라 여러 번 실행해도 안전하다.

## 🔴 표본 임계치 — `lib/tiers.ts` 단일 소스

| 표 | 단계 | 막대·% | 판정 카피 | 안내 |
|---|---|---|---|---|
| 서버 없음 | `offline` | — | — | 집계 서버가 연결되지 않아 결과를 표시하지 않습니다 |
| 0 | `empty` | — | — | 아직 아무도 안 눌렀습니다. 첫 표를 던져 보세요 |
| 1~19 | `counting` | — | — | 개표 중입니다. 아직 N표라 발표할 수 없습니다 |
| 20~49 | `partial` | ✅ | — | (투표 전) 지금까지 N명이 투표했습니다. 도장을 찍으면 결과가 보입니다 |
| 50+ | `full` | ✅ | ✅ | 〃 |

**참여자 수는 임계치와 무관하게 항상 노출한다.** 감출 것은 퍼센트지 참여 규모가 아니다.

### 임계치가 4곳에 자동으로 물리는 방법

`lib/seo.ts`의 **`outcome()` 안에 임계치를 넣었다.** 제목·설명·OG 카드·구조화 데이터가
전부 이 함수를 쓰므로 자동으로 따라온다. 호출부마다 조건을 복사하면 **반드시 한 곳이 어긋난다**
(실제로 `TURNOUT_THRESHOLD`가 그렇게 어긋나 있었다 → [[decisions]]).

### 화면은 두 조건을 모두 넘어야 결과를 낸다

`hasResult = showsResult(stage) && voted`. 임계치 + 내가 투표했는가.
수치는 메타가 담당하므로 검색 스니펫에서 사라지지 않는다.

## 🔴 투표 여부의 진실은 httpOnly 쿠키다

`localStorage`는 **첫 화면을 빠르게 그리는 힌트일 뿐**이고, `GET /api/vote` 응답으로 덮는다.

되돌리면 둘이 어긋나 사용자가 **"투표한 것처럼 보이는데 댓글도 못 쓰고 다시 투표도 못 하는"**
상태에 갇힌다. 실제로 그 버그가 있었다.

- 서버가 투표를 모르면 localStorage 힌트를 **지운다**
- 중복 투표 POST는 표를 더하지 않고 **원래 투표를 돌려준다** → 화면이 그 값으로 자기를 고친다
- **댓글 진영도 쿠키에서 읽는다.** 클라이언트를 믿으면 투표 없이 아무 진영으로 쓸 수 있다
- `voted`는 클라이언트 상태라 **서버 HTML에는 막대가 없다.** 재방문 투표자는 하이드레이션
  전까지 "도장을 찍으면 결과가 보입니다"를 잠깐 본다. 쿠키를 읽어 고치려면 페이지가
  매 요청 렌더로 바뀌므로 그대로 둔다

## 피드 순서 (`feedOrder`)

**진지 1 : 병맛 2**로 번갈아 짠다. 검색으로 들어온 사람은 진지 질문에 착지하므로,
투표 직후 **다음 자리에 병맛을 배치**해서 한 번 더 누르게 만든다.
진지만 이어지면 무겁고 병맛만 이어지면 가볍다.

각 갈래 안에서는 **표 많은 순**이다. 0표 질문이 첫 화면에 오면 죽은 사이트로 보인다.
같은 표 수면 배열 순서를 지킨다 — 매 요청 순서가 흔들리면 무한 스크롤에서 같은 질문이 두 번 나온다.

⚠️ **홈·상세·`/api/feed` 세 곳이 같은 순서를 써야 한다.** 어긋나면 중복이 뜬다.

## 한 화면 = 한 질문 (scroll-snap)

**문서(html)를 스크롤 컨테이너로** 쓴다. 별도 래퍼를 만들면 sticky 헤더와 푸터가
컨테이너 밖으로 밀려 레이아웃을 다시 짜야 한다. 스냅 지점(`.slide`)은 **홈 피드만** 내보내므로
다른 페이지는 영향을 받지 않고 클래스를 토글할 필요도 없다.

- `proximity`를 쓴다. `mandatory`는 긴 카드의 중간 내용을 도달 불가로 만든다([[decisions]])
- `100vh` 폴백 필수(모바일 주소창) · `scroll-snap-stop: always`(빠른 스와이프로 건너뛰기 방지)
- `prefers-reduced-motion`에서 스냅과 smooth를 **모두 해제**
- 키보드는 네이티브가 처리한다. 핸들러를 붙이지 않는다

### 🔴 카드는 슬라이드 높이를 **전부** 먹는다 (4차 §2)

`.slide > section:first-child { flex: 1 1 auto }`

이게 4차 개선의 핵심이었다. 슬라이드 높이는 처음부터 화면만 했지만
`justify-content: center`가 **400px 카드를 788px 슬라이드 중앙에 띄워** 놓았다.
무한 스크롤에서는 분산되던 여백이 한 화면 한 장이 되면서 위아래로 뭉쳤다.

카드에 `min-height`를 직접 주지 않는다 — 4장마다 붙는 광고 슬라이드에서
카드+광고가 화면을 넘어가 다음 카드가 안 걸친다([[decisions]]).

카드 **내부**는 `.question`·`.stats`의 `margin-top: auto` 두 개로 세 구역이 된다:
`머리글(문서번호) │ 질문·기표칸 │ 집계·버튼`. 남는 높이가 두 지점에 반씩 배분되므로
실제 서류처럼 머리글은 위, 서명란은 아래에 앉는다. ⚠️ 각 규칙 **안에** 써야 한다 —
`margin: 0`이 뒤에 오면 auto가 덮인다.

### 세로 배분 — 두 지침이 양립하지 않는다

1900×900 기준. 슬라이드 높이는 `calc(100dvh - 8.5rem)`이다.

| | px | % |
|---|---|---|
| sticky 헤더 (`--header-h` 3.2rem) | 51.2 | 5.7 |
| 헤더 여유 (`--header-gap` 0.7rem) | 11.2 | 1.2 |
| **카드** | **764** | **84.9** |
| 카드 간격 (`.stage` gap 1.1rem) | 17.6 | 2.0 |
| **다음 카드 걸침** | **56** | **6.2** |

4차 §6은 카드 75~80%, §3-2는 걸침 5~8%를 요구했는데 **합이 100%를 넘지 못해
동시에 성립하지 않는다.** 걸침을 택했다([[decisions]]) — 걸침이 없으면 첫 카드에서 이탈한다.
모바일 390×844도 카드 83.9% · 걸침 7.9%로 같이 맞는다.

높은 화면(1440px+)에 상한을 두지 않는다. 상한을 두면 카드를 다시 중앙에 띄워야 해서
위 문제가 되살아나고, `max-height`는 긴 질문에서 잘라낼 수도 없다.

### 🔴 헤더 높이와 스냅 오프셋은 **한 토큰**이다

globals.css `:root`의 `--header-h`(3.2rem) 하나가 두 곳에 쓰인다:

- `.masthead-bar { min-height: var(--header-h) }` — 헤더가 이보다 커질 수 없다
- `scroll-margin-top: var(--header-clear)` — `--header-h + --header-gap`(0.7rem)

**따로 두면 조용히 어긋난다.** 실제로 그랬다: 헤더 실측이 워드마크 라인박스 33.79px +
패딩 16px = 49.79px인데 스크롤하면 경계선 1px이 붙어 **50.79px**가 된다.
`scroll-margin-top`은 51.2px로 박혀 있었으니 여유가 **0.41px**였고,
Windows 배율 125·150%에서 반올림되며 **헤더가 카드 머리를 덮었다.**

카드가 슬라이드를 꽉 채우기 전에는 카드가 스냅 경계보다 195px 아래에 떠 있어서
드러나지 않았다 — 카드를 키우면서(4차 §2) 노출된 문제다.
z-index 문제로 보이지만 아니다. 헤더 `z-index: 10`이 최상위이고 그건 정상이다.

같은 원인이 **앵커 이동**에도 있었다. `#왜-그런지`(댓글 섹션)와 `#<슬러그>`(상세의
"다음 질문 →")는 `scroll-margin`이 아예 없어 대상이 y=0에 붙어 제목이 헤더에 가렸다.
→ `:target { scroll-margin-top: var(--header-clear) }` 한 줄로 전역 처리.

### 종이 폭은 홈만 넓다

`.stage`는 720px, **`.stage:has(.snap-feed)`만 894px**(카드 실폭 ≈ 859px).
약관·개인정보·댓글은 산문이라 한 줄이 길어지면 읽기 나빠진다.
`:has()`로 고르는 이유는 헤더·푸터가 같은 `.stage` 안이라 함께 넓어져야 정렬이 맞기 때문이다.
미지원 브라우저는 720px에 머문다(기능 손실 없음).

### 진행 표시는 sticky 헤더 안에 있다

`Feed`(클라이언트)가 `layout.tsx`의 `#feed-progress-slot`으로 **포털**한다.
전에는 헤더 아래에 따로 sticky로 떠서 소속이 불분명했다(4차 §3-1).
⚠️ 헤더 안이라 색 토큰이 `--ink-*`가 아니라 **`--room-*`**다 — 용지가 아니라 방에 붙어 있다.
다크에서 `--seal`은 `--room` 대비가 3.5:1로 작은 글씨에 부족해서 숫자도 `--room-ink`로 뺐다.

"↓ 다음 안건" 힌트는 **첫 슬라이드에만** 붙인다. 103장 전부면 소음이고, 한 번 넘겨 보면
제스처는 이미 학습된다.

## 색인 정책

`indexable(tally, commentCount)` = **표 20개 이상 그리고 댓글 1개 이상.**

**"또는"이 아니라 "그리고"다** — 표만 있고 댓글이 없으면 본문이 수치 두 줄뿐이라
여전히 빈 페이지다. 본문을 채우는 건 댓글이다.

- 미달이면 페이지가 `noindex, follow`를 낸다
- **사이트맵에도 통과한 질문만 넣는다.** 넣어 두고 noindex를 내면
  "이걸 보라" 한 뒤 "보지 마라"는 셈이라 크롤 예산만 태운다
- 홈·`/q`·`/best`·주제 허브·법적 고지는 항상 색인 허용
- 🔴 **닭-달걀처럼 보이지만 아니다.** 초기 트래픽은 커뮤니티 시딩이고, 시딩으로 표가 쌓이면
  색인이 자동으로 열린다. **SEO보다 시딩이 먼저다**

## 구조화 데이터

- `DiscussionForumPosting` — 질문 페이지. 결과를 `articleBody`, 댓글을 `comment`,
  투표 수를 `interactionStatistic`으로
- `WebSite` — 브랜드 검색에서 사이트명이 잡히게
- `BreadcrumbList` — 홈 > 질문 전체 > 주제 > 질문. 홈 항목은 **슬래시 없는 형태**로
  canonical과 맞춘다

🔴 **`FAQPage`·`QAPage`는 쓰지 않는다.** FAQ는 "답이 있는 질문"이고 QAPage는 이용자가
답변을 쓰는 Q&A용이다. 오용하면 리치리절트 자격이 박탈된다.

**종이는 항상 밝다.** 물리적 물건이니까. 어두워지는 건 기표소(`--room`)다.
다크에서 용지만 살짝 낮춘다(`#E7E3D9`).
