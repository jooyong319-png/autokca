# architecture — 라우트·데이터 흐름·규약

> 구조가 바뀌면 여기를 고친다([[SCHEMA]]). 코드와 다르면 코드가 맞다.

## 스택

Next.js 14 App Router · CSS 모듈 · TypeScript strict · Supabase(Postgres) · Vercel.
**의존성은 `next`·`react`·`react-dom` 셋뿐이다** — 나머지는 표준 API로 해결했다.

## 라우트

| 경로 | 렌더 | 역할 |
|---|---|---|
| `/` | ISR 60s | 피드. **scroll-snap 켜짐**(한 화면 = 한 질문) |
| `/q/[slug]` | SSG + `dynamicParams: true` | 질문 상세. **검색 착지 페이지.** 댓글 + 이어지는 피드(스냅 켬, 진행 표시 없음) |
| `/q` | ISR 1h | 질문 전체 목록 |
| `/c/[topic]` | SSG | 주제 허브 8개. 크롤 경로 + "돈 관련 투표 모음" 롱테일 |
| `/best` | ISR 30m | 집계 — 팽팽한/몰린/표 많은 질문 TOP 10 |
| `/me` | 정적 · **noindex** | 성향 확인서. 브라우저 기록만 씀 |
| `/about` `/terms` `/privacy` | 정적 | 법적 고지 |
| `not-found.tsx` | 정적 · 자동 `noindex` | **반송 통지 + 안건 8건 링크.** 순수 서버 컴포넌트다(아래) |
| `/api/vote` | dynamic | `GET`=내 투표 상태 · `POST`=투표·**번복**. DELETE·PUT·PATCH는 없다(405) — 취소를 만들지 않는다 |
| `/api/comments` | dynamic | `GET`=폴링 목록+tops+counts · `POST`=작성 · `[id]` `PATCH`=공감·신고 |
| `/api/feed` | dynamic | 무한 스크롤 다음 묶음 |
| `/api/stats` | ISR 5m | 누적 표 수(푸터) |
| `/opengraph-image` · `/q/[slug]/opengraph-image` | **dynamic** | 공유 카드 |

⚠️ **`dynamicParams`는 `true`여야 한다.** `false`면 질문을 추가해도 재배포 전까지 404가 난다.
범위 밖 슬러그는 `notFound()`가 막으므로 soft-404 위험은 없다.

⚠️ **OG 라우트는 `force-dynamic`이다.** 빌드 프리렌더를 시도하면 Windows에서
`@vercel/og`가 빌드 자체를 실패시킨다(통합 위키 `nextjs.md` 참고).

## 데이터 흐름

```
lib/questions.ts (질문 103개 · 코드에 박혀 있다)
        │
        ├─ feedOrder(exclude, votesOf) ── 진지 1 : 병맛 2, 각 갈래는 표 많은 순
        │
        ▼
서버 컴포넌트 ──▶ lib/votes.ts ──┐
                lib/comments.ts ─┤── lib/supabase.ts ──▶ PostgREST RPC
                                 │        (환경변수 없으면 전부 null)
                                 ▼
                          Supabase: tallies · comments
```

**질문은 DB에 없다.** 코드에 있다. DB에는 집계(`tallies`)와 댓글(`comments`)만 있다.
그래서 질문을 고치려면 배포해야 하고, 그게 "발행은 수동"([[SCHEMA]] 제2원칙)과 맞물린다.

### Supabase는 서버만 만진다

`service_role` 키로 PostgREST **RPC만** 호출한다. SDK를 넣지 않았다 — 하는 일이
"카운터 읽고 올리기 + 댓글 CRUD"뿐이라 의존성 값이 없다.

- **원자적 증가**를 DB 함수에 맡긴다. 읽고 나서 쓰면 동시 투표가 유실된다
- 브라우저는 DB를 직접 만지지 않는다. anon 키를 노출하지 않는다
- **환경변수가 없어도 사이트가 돌아간다** — 결과를 감추고 그 사실을 화면에 밝힌다
- ⚠️ **PostgREST `max-rows` 기본 1000.** `all_tallies`·`all_comment_counts`는 질문이
  1000개를 넘으면 조용히 잘린다. 그때는 페이지네이션이나 사전 계산이 필요하다

스키마는 `supabase/schema.sql`이 소스 오브 트루스다(사람이 SQL Editor에서 1회 실행).
`create or replace`라 여러 번 실행해도 안전하다.

### 🔴 UX 게이트와 SEO 게이트는 값이 다르다 (6차 §1-1)

| 상수 | 값 | 성격 |
|---|---|---|
| `TIER.RESULT` | **5표** | UX — 퍼센트·막대 |
| `TIER.VERDICT` | **20표** | UX — 판정 카피 |
| `TIER.INDEX` | **20표 + 댓글 1개** | SEO — `noindex` 해제 |

**사용자는 결과를 보는데 크롤러는 아직 못 보는 상태가 정상이다.**
전에는 RESULT와 INDEX가 둘 다 20이라 사실상 한 게이트였고, 화면이 비면 색인도 같이 막혀
따로 조절할 수 없었다.

2026-08-13 하향(RESULT 20→5, VERDICT 50→20): 원래 목적은 "1표에 100%"를 막는 것이었는데
값이 과해 **카드에 채울 내용을 통째로 가렸다.** 실측으로 상위 카드가 4표라 막대·판정이
전부 0개였고, 투표해도 "개표 중입니다"만 떴다 — 투표의 보상이 결과인데 그걸 안 주면
다음 카드로 넘어갈 이유도 사라진다.

객체를 `UX_THRESHOLDS`/`SEO_THRESHOLDS` 둘로 쪼개지 않았다. 값이 갈라지면 분리는 이미
달성되고, 둘로 나누면 `stageOf`가 두 곳을 참조해 **한 파일에 모아 둔 이유**가 약해진다.

⚠️ 화면 문구에 숫자를 하드코딩하지 않는다. `Ballot.tsx`에 `50`이 박혀 있어서
임계치를 내렸을 때 문구만 옛 값으로 남을 수 있었다 → `TIER.VERDICT` 참조로 바꿨다.

**참여자 수는 임계치와 무관하게 항상 노출한다.** 감출 것은 퍼센트지 참여 규모가 아니다.

### 임계치가 4곳에 자동으로 물리는 방법

`lib/seo.ts`의 **`outcome()` 안에 임계치를 넣었다.** 제목·설명·OG 카드·구조화 데이터가
전부 이 함수를 쓰므로 자동으로 따라온다. 호출부마다 조건을 복사하면 **반드시 한 곳이 어긋난다**
(실제로 `TURNOUT_THRESHOLD`가 그렇게 어긋나 있었다 → [[decisions]]).

### 화면은 두 조건을 모두 넘어야 결과를 낸다

`hasResult = showsResult(stage) && voted`. 임계치 + 내가 투표했는가.
수치는 메타가 담당하므로 검색 스니펫에서 사라지지 않는다.

## 카드의 댓글 미리보기 (6차 §2-1)

양 진영 1위 댓글을 카드에 한 줄씩. 진영 분리가 최대 차별점인데(브리프 §4)
상세에 들어가야만 보이던 것을 피드로 끌어올린다.

- `all_top_comments()` **배치 RPC** — 카드마다 `top_comment`를 두 번 부르면 3장에 왕복 6번이다.
  정렬 기준을 `top_comment`와 **동일하게** 맞춘다(카드와 상세의 1위가 다르면 버그로 읽힌다)
- 🔴 **서버에서 넣는다.** 클라이언트가 나중에 채우면 카드 높이가 바뀌고
  그게 scroll-snap 위치를 무너뜨린다
- 🔴 **댓글이 없어도 자리를 비우지 않는다.** 카드 높이가 카드마다 달라지면 스냅이 흔들린다 —
  빈 상태 문구("아직 이유를 밝힌 사람이 없습니다")가 자리를 지킨다
- ⚠️ **투표 전에는 진영 이름을 감춘다**("한쪽"/"다른쪽"). 어느 쪽이 우세한지 먼저 보이면
  밴드왜건이 생긴다 — 막대를 투표 후에만 보여주는 것과 같은 이유다
- 상세의 **주 카드**는 이미 받아 온 `topA`/`topB`를 재사용한다(추가 왕복 0)
- RPC가 없으면 `rpc()`가 null → 빈 Map → 빈 상태. **SQL 실행 전에 배포해도 안 깨진다**

미리보기는 `Comment`를 재사용하지 않고 `TopPreview`(id·body·likes)를 쓴다 —
`createdAt`이 필요 없는데 타입을 맞추려 빈 문자열을 넣으면 **없는 값을 있는 것처럼** 만든다.

## 🔴 투표 여부의 진실은 httpOnly 쿠키다

`localStorage`는 **첫 화면을 빠르게 그리는 힌트일 뿐**이고, `GET /api/vote` 응답으로 덮는다.

되돌리면 둘이 어긋나 사용자가 **"투표한 것처럼 보이는데 댓글도 못 쓰고 다시 투표도 못 하는"**
상태에 갇힌다. 실제로 그 버그가 있었다.

- 서버가 투표를 모르면 localStorage 힌트를 **지운다**
- 중복 투표 POST는 표를 더하지 않고 **원래 투표를 돌려준다** → 화면이 그 값으로 자기를 고친다
- **댓글 진영도 쿠키에서 읽는다.** 클라이언트를 믿으면 투표 없이 아무 진영으로 쓸 수 있다
- `voted`는 클라이언트 상태라 **서버 HTML에는 막대가 없다.** 재방문 투표자는 하이드레이션
  전까지 "도장을 찍으면 결과가 보입니다"를 잠깐 본다. 쿠키를 읽어 고치려면 페이지가
  매 요청 렌더로 바뀌므로 그대로 둔다

## 🔴 기표 번복은 되고 **취소는 안 된다** (2026-08-13)

- **번복** — 다른 쪽을 누르면 한 쪽에서 빼고 다른 쪽에 더한다(`change_vote` RPC).
  감소·증가를 **한 update 안에서** 한다. 두 번 왕복하면 그 사이 합계가 틀린다.
- **취소** — 그런 경로를 만들지 않는다. `/api/vote`는 `GET`·`POST`만 있고
  DELETE·PUT·PATCH는 405다. 집계에서 표가 사라지면 "아까 N명이었는데"라는 의심이 생기고,
  그건 이 사이트가 파는 유일한 것(집계 신뢰)을 깎는다.
- 같은 쪽을 다시 누르면 **아무 일도 일어나지 않는다.** "다시 눌러 해제"가 되면 취소가 된다.

### 사유를 제출하면 기표가 잠긴다

댓글 진영은 기표 쿠키에서 읽으므로(`/api/comments` POST) 사유를 낸 뒤 번복하면
**자기가 쓴 의견이 "반대편" 칼럼에 남는다.** 자기 주장이 상대 진영 것으로 표시되는
앞뒤 안 맞는 상태다. 의견은 그 시점의 판단을 기록한 것이니 옮기지도 않는다.
→ 사유 제출 전까지는 얼마든지 바꾸고, 낸 뒤에는 그 입장에 남는다(409 + 이유 문구).

### 🔴 반영을 확인한 **뒤에** 쿠키를 심는다

`rpc()`는 실패하면 null을 주고 `changeVote`/`castVote`는 `EMPTY`(`live: false`)를 돌려준다.
그때 쿠키를 바꾸면 **쿠키는 새 진영, DB는 옛 진영**이 되어 영구히 어긋난다 —
그 사람의 표는 반대쪽에 남아 있는데 화면과 댓글 진영은 새 쪽을 가리킨다.
→ `!tally.live`면 쿠키를 건드리지 않고 503을 낸다.

신규 기표에도 같은 구멍이 있었다: 집계가 죽어 있어도 쿠키가 박혀서 **표는 세지 않은 채
기표한 것으로 남았고**, 서버가 돌아온 뒤에도 다시 기표할 수 없었다. 같이 고쳤다.

실측(검증 후 행 삭제): 신규 200·a=1 → 같은 쪽 재클릭 200·a=1(안 늘어남) →
`change_vote` 없는 상태에서 번복 시도 503·쿠키 `a` 유지·DB 그대로 → DELETE/PUT/PATCH 405.

### 남용 방지 (7차 §2-5)

- **질문당 3회.** 번복의 목적은 오터치 복구다 — 그 이상은 집계를 흔드는 놀이가 된다.
  `r_<id>` 쿠키에 횟수를 센다.
- **쿨다운 4초.** `rc_<id>` 쿠키의 **만료 자체가 쿨다운**이다 — 타임스탬프를 넣고 비교하면
  시계 차이·문자열 파싱이 새 실패 지점이 된다. 있으면 쿨다운 중, 없으면 끝난 것.
- 카피 "말을 바꾸셨습니다. **기록에 남습니다.**" — 실제로 남긴다(위 횟수 쿠키).
  카피가 사실이 아니면 그것도 숫자를 지어내는 일이다.

### 🔴 `/api/vote`는 캐시된 집계를 쓰지 않는다

`readTally`는 기본 `revalidate: 60`이다. 그대로 쓰면 방금 들어간 표가 안 보이는 값을
돌려주고, 화면은 "서버가 진실"이라는 규칙대로 **그 낡은 값으로 자기를 덮는다.**
실측에서 DB가 `a=1`인데 응답이 `a=0`이었다.
→ `readTally(id, true)`로 캐시를 건너뛴다. 페이지 렌더(ISR)에서는 60초 캐시가 맞으므로 기본값은 그대로.

### 다수파 기록(`/me`)은 번복 시 횟수를 늘리지 않는다

`<id>:counted`에 **어느 선택으로 반영했는지**를 남기고 그것과 다를 때만 손댄다.
번복이면 총 참여 횟수(`n`)는 그대로 두고 다수파 여부(`major`)만 고친다 —
한 사람이 한 번 참여한 것이지 두 번이 아니다. 마운트 단위 ref로는 막을 수 없어서
localStorage 기록으로 바꿨다.

## 🔴 홈 첫 카드는 상위권 안에서 **매일 회전**한다 (2026-08-14)

`questionOfDay(rankedSerious, seoulDayKey())`

전에는 표 1위가 그대로 첫 카드였다. 그런데 **첫 카드가 노출을 가장 많이 받아 표를 가장
많이 얻고, 그래서 계속 첫 카드**가 된다 — 1등이 1등이라서 1등인 잠금이다.
재방문자는 미투표 우선 정렬이 풀어 주지만 **신규 방문자는 영원히 같은 첫인상**을 받고,
브리프 §3의 시의성("매일 방문할 이유")을 만들 장치가 없었다.

| 결정 | 왜 |
|---|---|
| 전체가 아니라 **상위 8개** 안에서 | 완전 회전이면 0표짜리가 첫 화면에 올 수 있다 = 죽은 사이트 인상 |
| 무작위가 아니라 **날짜** | `Math.random()`이면 새로고침마다 바뀌어 ISR 캐시가 무의미하고, "오늘의 안건"으로 인식되지 않는다 |
| 해시가 아니라 **날짜 순번** | 해시는 충돌로 이틀 연속 같은 안건이 나온다(실측 확인). 순번은 한 바퀴 돌 때까지 안 겹친다 |
| UTC가 아니라 **KST** | UTC면 오전 9시에 바뀐다. 자정에 바뀌어야 "오늘"이 말이 된다 |
| 후보를 **id 순**으로 정렬 후 인덱싱 | 표 순으로 하면 하루 중 표가 움직일 때마다 첫 카드가 갈린다 |

0표는 후보에서 빼고, 후보가 2개 미만이면 회전하지 않는다(돌릴 만큼 쌓이지 않았다).
**순서만 정한다 — 집계는 건드리지 않는다**(제1원칙).

실측(24일): 연속 중복 0회, 후보 8개가 3일씩 균등 노출.

## 피드 순서 (`feedOrder`)

**진지 1 : 병맛 2**로 번갈아 짠다. 검색으로 들어온 사람은 진지 질문에 착지하므로,
투표 직후 **다음 자리에 병맛을 배치**해서 한 번 더 누르게 만든다.
진지만 이어지면 무겁고 병맛만 이어지면 가볍다.

각 갈래 안에서는 **표 많은 순**이다. 0표 질문이 첫 화면에 오면 죽은 사이트로 보인다.
같은 표 수면 배열 순서를 지킨다 — 매 요청 순서가 흔들리면 무한 스크롤에서 같은 질문이 두 번 나온다.

⚠️ **홈·상세·`/api/feed` 세 곳이 같은 순서를 써야 한다.** 어긋나면 중복이 뜬다.

## 한 화면 = 한 질문 (scroll-snap)

**문서(html)를 스크롤 컨테이너로** 쓴다. 별도 래퍼를 만들면 sticky 헤더와 푸터가
컨테이너 밖으로 밀려 레이아웃을 다시 짜야 한다. 스냅 지점(`.slide`)은 **피드만** 내보내므로
다른 페이지는 영향을 받지 않고 클래스를 토글할 필요도 없다.

- `proximity`를 쓴다. `mandatory`는 긴 카드의 중간 내용을 도달 불가로 만든다([[decisions]])
- `100vh` 폴백 필수(모바일 주소창) · `scroll-snap-stop: always`(빠른 스와이프로 건너뛰기 방지)
- `prefers-reduced-motion`에서 스냅과 smooth를 **모두 해제**
- 키보드는 네이티브가 처리한다. 핸들러를 붙이지 않는다

### 🔴 카드는 슬라이드 높이를 **전부** 먹는다 (4차 §2)

`.slide > section:first-child { flex: 1 1 auto }`

이게 4차 개선의 핵심이었다. 슬라이드 높이는 처음부터 화면만 했지만
`justify-content: center`가 **400px 카드를 788px 슬라이드 중앙에 띄워** 놓았다.
무한 스크롤에서는 분산되던 여백이 한 화면 한 장이 되면서 위아래로 뭉쳤다.

카드에 `min-height`를 직접 주지 않는다 — 4장마다 붙는 광고 슬라이드에서
카드+광고가 화면을 넘어가 다음 카드가 안 걸친다([[decisions]]).

카드 **내부**는 `.question`·`.stats`의 `margin-top: auto` 두 개로 세 구역이 된다:
`머리글(문서번호) │ 질문·기표칸 │ 집계·버튼`. 남는 높이가 두 지점에 반씩 배분되므로
실제 서류처럼 머리글은 위, 서명란은 아래에 앉는다. ⚠️ 각 규칙 **안에** 써야 한다 —
`margin: 0`이 뒤에 오면 auto가 덮인다.

### 세로 배분 — 두 지침이 양립하지 않는다

1900×900 기준. 슬라이드 높이는 `calc(100dvh - 8.5rem)`이다.

| | px | % |
|---|---|---|
| sticky 헤더 (`--header-h` 3.2rem) | 51.2 | 5.7 |
| 헤더 여유 (`--header-gap` 0.7rem) | 11.2 | 1.2 |
| **카드** | **748** | **83.1** |
| 카드 간격 (`.slide` margin-bottom 1.6rem) | 25.6 | 2.8 |
| **다음 카드 걸침** | **64** | **7.1** |

모바일 390×844는 카드 82.0% · 걸침 7.6%, 1080 세로는 85.9% · 5.9% —
걸침이 64px로 일정하고 세 해상도 모두 구간 안이다.

🔴 **카드 간격은 `.slide`가 스스로 갖는다.** `.stage { gap: 1.1rem }`은 슬라이드에
적용되지 않는다 — 슬라이드는 `.stage`의 직계 자식이 아니라 Feed 래퍼(`.snap-feed`)
안에 있고 그 래퍼는 flex가 아니다. 이걸 착각해서 있지도 않은 간격을 계산에 넣었고,
실제로는 **카드끼리 맞붙어** 있었다. 별개의 서류인데 경계가 없으면 한 장처럼 보인다.
`margin`은 스냅 정렬에 영향을 주지 않는다(그건 `scroll-margin`이다).

"↓ 다음 안건" 힌트는 `position: absolute`로 그 간격 안에 앉힌다. 흐름에 두면
**첫 카드만 그만큼 짧아져서** "1↔2에는 공간이 있는데 2↔3에는 없다"가 된다.

4차 §6은 카드 75~80%, §3-2는 걸침 5~8%를 요구했는데 **합이 100%를 넘지 못해
동시에 성립하지 않는다.** 걸침을 택했다([[decisions]]) — 걸침이 없으면 첫 카드에서 이탈한다.
모바일 390×844도 카드 83.9% · 걸침 7.9%로 같이 맞는다.

높은 화면(1440px+)에 상한을 두지 않는다. 상한을 두면 카드를 다시 중앙에 띄워야 해서
위 문제가 되살아나고, `max-height`는 긴 질문에서 잘라낼 수도 없다.

### 🔴 헤더 높이와 스냅 오프셋은 **한 토큰**이다

globals.css `:root`의 `--header-h`(3.2rem) 하나가 두 곳에 쓰인다:

- `.masthead-bar { min-height: var(--header-h) }` — 헤더가 이보다 커질 수 없다
- `scroll-margin-top: var(--header-clear)` — `--header-h + --header-gap`(0.7rem)

**따로 두면 조용히 어긋난다.** 실제로 그랬다: 헤더 실측이 워드마크 라인박스 33.79px +
패딩 16px = 49.79px인데 스크롤하면 경계선 1px이 붙어 **50.79px**가 된다.
`scroll-margin-top`은 51.2px로 박혀 있었으니 여유가 **0.41px**였고,
Windows 배율 125·150%에서 반올림되며 **헤더가 카드 머리를 덮었다.**

카드가 슬라이드를 꽉 채우기 전에는 카드가 스냅 경계보다 195px 아래에 떠 있어서
드러나지 않았다 — 카드를 키우면서(4차 §2) 노출된 문제다.
z-index 문제로 보이지만 아니다. 헤더 `z-index: 10`이 최상위이고 그건 정상이다.

같은 원인이 **앵커 이동**에도 있었다. `#왜-그런지`(댓글 섹션)와 `#<슬러그>`(상세의
"다음 질문 →")는 `scroll-margin`이 아예 없어 대상이 y=0에 붙어 제목이 헤더에 가렸다.
→ `:target { scroll-margin-top: var(--header-clear) }` 한 줄로 전역 처리.

### 종이 폭은 **모든 페이지에서 같다** (2026-08-13 결정)

`.stage`는 720px, **`.stage:has(.ballot)`만 894px**(카드 실폭 ≈ 859px).

기준이 "스냅 피드가 있나"가 아니라 **"투표용지가 있나"**다. 처음엔 홈만 넓혔는데
**상세가 구버전으로 남았다** — 검색 유입은 대부분 상세로 착지하므로(브리프 원칙 1)
그게 첫인상인데 홈과 딴 사이트처럼 보였다.

| 페이지 | 폭 | 왜 |
|---|---|---|
| `/`, `/q/[slug]` | 894px | 투표용지가 주인공 |
| `/q`, `/best`, `/c/[topic]` | 720px | 목록이다 |
| `/about`, `/terms`, `/privacy` | 720px | 산문이라 한 줄이 길면 읽기 나빠진다 |

`:has()`로 고르는 이유는 헤더·푸터가 같은 `.stage` 안이라 함께 넓어져야 정렬이 맞기 때문이다.
전역 `ballot` 클래스는 `Ballot`의 루트에 붙는다(CSS 모듈 해시와 별개).
미지원 브라우저는 720px에 머문다(기능 손실 없음).

### 상세의 주 투표용지는 70dvh — 댓글이 보여야 한다

`.standalone { min-height: 70dvh }`. 홈처럼 83%까지 키우지 **않는다.**

그러면 댓글이 완전히 접힌다 — 진영 분리 댓글이 최대 차별점이고(브리프 §4)
SEO 본문이자 체류시간이다. 70dvh면 1900×900에서 카드 아래로 댓글 섹션이 약 143px,
390×844에서 126px 보인다. "카드가 주인공이지만 아래에 뭔가 더 있다"가 동시에 성립한다.

이어지는 피드의 카드들에는 걸지 않는다 — 자유 스크롤로 훑는 자리다(3차 §2-8).

### 🔴 헤더는 `fixed`다 — sticky는 containing block에 갇혔다 (7차 §5-3)

`.masthead-bar`가 `sticky`였을 때 **스크롤하면 헤더가 사라졌다.** 원인은
`overflow` 컨테이너가 아니라(그런 래퍼는 없다) **sticky의 containing block**이었다:
부모가 `.masthead`(바 51px + 태그라인 24px ≈ 78px)라 **27px만 스크롤하면 구간이 끝났다.**

→ `.masthead { position: fixed }`. 부모와 무관하게 뷰포트에 붙는다.
7차 문서가 제안한 **별도 스크롤 컨테이너는 채택하지 않았다** — 헤더·푸터가 그 밖으로
밀려 레이아웃을 다시 짜야 하고, 그건 위의 "문서를 스크롤 컨테이너로 쓴다" 결정을 되돌린다.

`fixed`가 되면서 따라온 것들:

| 무엇 | 왜 |
|---|---|
| `.stage { padding-top: calc(var(--header-h) + 0.9rem) }` | `fixed`는 흐름에서 빠져 자리를 안 차지한다 |
| `--stage-w` 토큰 + **`body`**`:has(.ballot)` | 헤더가 `.stage` 밖이라 `.stage:has()`로는 폭을 못 받아 워드마크와 카드가 어긋난다 |
| `html { scroll-padding-top: var(--header-clear) }` | `.slide`·`:target`의 `scroll-margin-top` 두 곳을 한 곳으로. 새 앵커를 만들 때마다 기억할 필요가 없다 |
| `.masthead-bar { line-height: 1 }` | 상속 1.6이면 워드마크 라인박스가 33.8px가 되고 `align-items: baseline`에서 콘텐츠가 `--header-h`를 넘을 수 있다 → 넘으면 스냅 오프셋이 다시 어긋난다 |

### 헤더 목차 (7차 §5)

`components/HeaderNav.tsx` — **3개만**: 집계(`/best`) · 안건(`/q`) · 확인서(`/me`).
소개·약관·개인정보는 푸터에 이미 있다. 6개를 넣으면 선택 피로만 생긴다.

- 현재 위치는 **빨간 밑줄** + `aria-current="page"`. 글자색은 `--room-ink`다 —
  `--seal`은 `--room` 위에서 4.39:1로 이 크기에 미달한다. **색이 아니라 선이 정보를 나른다.**
- `/q`는 `/q/[slug]`의 부모지만 **정확히 일치할 때만** 켠다(상세에서 목록에 있는 것처럼 읽힌다).
- 클라이언트 컴포넌트인 이유는 `usePathname()` 하나뿐이다.

### 진행 표시는 헤더 안에 있다

`Feed`(클라이언트)가 `layout.tsx`의 `#feed-progress-slot`으로 **포털**한다.
전에는 헤더 아래에 따로 sticky로 떠서 소속이 불분명했다(4차 §3-1).
⚠️ 헤더 안이라 색 토큰이 `--ink-*`가 아니라 **`--room-*`**다 — 용지가 아니라 방에 붙어 있다.
다크에서 `--seal`은 `--room` 대비가 3.5:1로 작은 글씨에 부족해서 숫자도 `--room-ink`로 뺐다.

"↓ 다음 안건" 힌트는 **첫 슬라이드에만** 붙인다. 103장 전부면 소음이고, 한 번 넘겨 보면
제스처는 이미 학습된다.

## 404 — 반송 통지 (`app/not-found.tsx`)

Next 기본 에러 페이지를 쓰지 않는 이유 두 개:

1. **기본 에러 페이지는 다크다.** 프레임워크가
   `@media (prefers-color-scheme: dark) { body { background:#000 } }`를 직접 넣는다.
   사이트는 라이트 하나인데 404만 새까맸다. 레이아웃이 감싸므로 헤더·푸터는 밝고
   가운데만 검은 더 이상한 상태였다.
2. **막힌 길이었다.** 영문 "This page could not be found" 한 줄뿐이라
   검색·외부 링크로 들어온 사람이 여기서 끝났다. 브리프 원칙 2(돌려보내지 않는다)에 어긋난다.

### 🔴 여기서는 DB를 읽지 않고 클라이언트 컴포넌트도 쓰지 않는다

처음엔 홈처럼 집계를 받아 `<Feed>`로 투표용지를 깔았다. 그런데
**페이지 안에서 `notFound()`가 던져지는 경로**(`/q/<없는슬러그>`·`/c/<없는주제>`)에서는
**클라이언트 컴포넌트가 서버 렌더되지 않아** 통지만 남고 안건이 통째로 사라졌다.
라우트가 아예 없는 `/nonexistent`에서는 정상이라 더 헷갈렸다.

| 경로 | `Feed`(클라이언트) 서버 렌더 |
|---|---|
| `/nonexistent` (라우트 없음) | 됨 |
| `/q/<없는슬러그>` (`notFound()`) | **안 됨** |
| `/c/<없는주제>` (`notFound()`) | **안 됨** |

하필 잘못된 질문 주소가 가장 흔한 404다. 그래서 **질문이 코드에 있다는 점**을 이용해
(`lib/questions.ts` — DB에 없다) 순수 서버 컴포넌트 링크 목록으로 만들었다.
집계를 읽지 않으므로 `feedOrder()`에 `votesOf`를 넘기지 않고 배열 순서를 쓴다
(진지 1 : 병맛 2 교차는 유지된다).

부수 효과: 크롤러에게 내부 링크를 주고, 하이드레이션 불일치 위험이 없고, 페이지가 가볍다.
목록에서 상세로 가면 투표용지·댓글·이어지는 피드가 다 있으므로 깔때기는 정상 경로로 합쳐진다.

## 투표 직후 카드에서 바로 쓴다 (7차 §3)

`components/CardSay.tsx` — 카드 안 한 줄 입력. 전에는
`투표 → 링크 → 상세 이동 → 스크롤 → 입력창 발견`이라 단계마다 이탈했고,
**투표 직후가 가장 말하고 싶은 순간**인데 30초면 사라졌다.

- **결과가 먼저** — `hasResult`일 때만 렌더하고 CSS로 0.3s 늦춘다.
  결과가 투표의 보상인데 입력창이 같이 뜨면 거래처럼 느껴진다
- **자동 포커스 금지** — 모바일에서 키보드가 즉시 올라오면 화면 절반이 가려져
  방금 받은 결과를 볼 수 없다
- **다음 안건으로 가는 조건이 아니다** — 매번 글을 요구하면 3개쯤에서 지친다.
  유도는 하되 우회로는 항상 열려 있다
- 한 줄 `input`(80자). `textarea`는 "글을 써야 한다"는 부담을 준다
- 플레이스홀더 4종. **팽팽(±5%)을 소수파보다 먼저** 판정한다 — 소수파여도 반반이면
  "소수 의견"이 아니다. 소수파 유도가 가장 잘 작동한다
- 최소 길이 **5자**(2자에서 올림). "ㅇㅈ"만 쌓이면 SEO 본문 역할을 못 한다.
  대가로 "당연하죠"(4자)도 막힌다
- 진영은 여전히 **서버가 쿠키에서** 읽는다. 클라이언트가 보내면 투표 없이 아무 진영으로 쓸 수 있다

## 사유를 올리면 상세의 내 댓글로 착지한다 (8차)

`카드에서 한 줄 → 0.9초 확인 → /q/{slug}#c-{id}`

- **실제 생성된 댓글을 보여준 뒤** 이동한다. POST 응답에 id·body가 있으므로
  낙관적 표시가 필요 없고, 따라서 **롤백할 상태도 없다**(8차 §7이 요구한 처리가 불필요해진다)
- 0.9초 기다리는 이유: 누르자마자 화면이 바뀌면 등록됐는지 확인하지 못하고,
  모바일에서 한 번 깜빡이면 "오류가 났나" 하는 불안을 준다
- 착지는 **최상단이 아니라 내 댓글**이다. 맨 위로 보내면 질문을 다시 읽게 된다
- 하이라이트는 **`:target` CSS**다. JS 타이머로 클래스를 붙이면 뒤로가기·새로고침에서
  어긋나고 같은 앵커를 다시 열 때 안 켜진다. reduced-motion에서는 움직임만 끄고
  **표시는 남긴다** — 없애면 기능이 사라진다
- `.item { scroll-margin-top: 7rem }` — `html`의 `scroll-padding-top`에 **더해진다.**
  딱 맞게 착지하면 "내 글"만 보이고 "반대편 의견"이 화면 밖에 남는다. 둘이 한 화면에 들어와야
  이 이동에 의미가 있다
- 실패하면 **이동하지 않는다.** 카드에 머물며 에러를 보이고 입력 내용을 보존한다 —
  이동한 뒤 "등록 실패"가 뜨는 것이 최악이다
- ⚠️ 상세의 **주 카드에는 `CardSay`를 렌더하지 않는다.** 그 페이지엔 진짜 댓글 폼이 있어
  입력창이 둘이 된다. 이어지는 피드의 카드들은 다른 안건이므로 그대로 보여준다

### 🔴 `Comments`는 마운트 즉시 한 번 받아온다

전에는 `setInterval(pull, 6000)`만 걸어서 **첫 조회가 6초 뒤**였다. 상세는
ISR 300초 + 목록 60초 캐시라 서버 HTML이 최대 5분 낡을 수 있고, 특히 위 흐름으로
넘어오면 **자기 댓글이 없는 화면에 도착**한다.

### 카드 사이 간격은 Feed 래퍼가 준다

`.wrap { display: flex; gap: 1.6rem }`.
처음엔 `.slide { margin-bottom }`으로 홈만 고쳤는데 **상세는 스냅이 꺼져 있어 `.slide`가
없다**(Fragment로 렌더된다) → 상세의 "이어지는 안건"들이 계속 맞붙어 있었다.
래퍼에 두면 스냅 여부와 무관하게 한 곳에서 해결된다.

## 미투표 우선 정렬 — ISR을 어떻게 우회했나

홈이 쿠키를 읽으면 `revalidate = 60`을 잃는다(가장 많이 열리는 페이지다).
→ **홈의 서버 씨앗을 1장으로 줄이고**, 2장부터는 `/api/feed`(이미 `force-dynamic`이라
잃을 캐시가 없다)가 쿠키를 읽어 미투표를 앞으로 정렬한다.

- `feedOrder(exclude, votesOf, voted)` — 정렬은 **갈래 안에서만**.
  진지 1 : 병맛 2 교차가 유지되어야 한다
- `readVotedIds()` — 쿠키는 기표한 안건에만 있으므로 이름만 훑는다(103개 순회 불필요)
- 홈은 `excludeId`로 심은 카드를 뺀다. 개인화/비개인화 순서가 달라 안 빼면 중복이 난다
- 🔴 **투표한 것을 숨기지 않는다.** 결과 변화가 핵심 재방문 이유다. 순서만 뒤로 보내고
  "처리됨" 도장으로 표시한다(절대 배치 — 하이드레이션 후 켜지므로 흐름에 넣으면 높이가 바뀐다)

### `/me` 기표 내역

안건별로 **내가 고른 쪽 · 현재 내 비율 · 소수/다수 · 총 표수**. 전에는 집계 요약만 있어
"내가 투표한 목록"을 볼 곳이 없었다.

- **소수파 먼저** 정렬. 자기가 소수였던 안건이 가장 재미있고 다시 보러 올 이유가 된다
- `revalidate` 3600 → 300. 현재 비율을 붙이므로 1시간 낡은 값은 "지금"과 어긋난다.
  누구에게나 같은 HTML이라(개인화는 전부 클라이언트) ISR 효율은 그대로다
- 서버는 **누가 무엇을 골랐는지 모른다.** 안건·집계만 내려주고 맞추는 일은 브라우저에서

### 🔴 `/me`의 "당시 비율"은 영구히 불가능하다 (2026-08-13 결정)

투표 시점의 비율을 **기록하지 않기로 했다.** 따라서 "당시 vs 현재 비율"과
"여론이 뒤집힌 안건"은 만들 수 없다 — 근거 데이터가 없고 지어내면 제1원칙 위반이다.
`/me`는 투표 목록 · 내 선택 · **현재** 비율 · 소수파 모음까지만 만든다.
`ottoke:voted`에 무엇에 어떻게 투표했는지는 이미 다 있다.

### 🔴 분석 태그는 `next/script`를 쓰지 않는다

`components/Analytics.tsx` — `<head>`에 **생 `<script>`**로 박는다.

⚠️ `curl | grep googletagmanager`는 preload·RSC 문자열에도 걸려 **통과한다.**

- 운영 배포에서만 로드한다: `VERCEL_ENV !== 'production'`이면 `null`.

`X-Frame-Options`에는 예외를 둘 수 없다(`ALLOW-FROM`은 폐기). CSP `frame-ancestors`로 바꿨다.
⚠️ **두 헤더를 함께 두지 않는다** — 브라우저마다 우선순위가 갈려 CSP가 무력해질 수 있다.

## 안건은 **코드 + DB** 두 곳에서 온다 (2026-08-15)

`lib/catalog.ts`의 `catalog()` = 코드 103개(`lib/questions.ts`) + DB 발행분(`drafts`).

### 🔴 왜 전부 DB로 옮기지 않았나

**Supabase가 죽는 순간 질문이 하나도 없는 빈 사이트가 된다.** 지금 설계는 집계만 감추고
질문은 보인다 — 제1원칙의 "죽으면 감추고 밝힌다"와 같은 결이다.
코드의 103개가 항상 있는 바닥이고, 관리 화면에서 발행한 것이 그 위에 얹힌다.
DB가 죽으면 `publishedDrafts()`가 빈 배열을 주고 사이트는 103개로 계속 돈다.

### ⚠️ 점검 스크립트가 여기서 오탐을 낸다

`/api/stats`의 `questions`는 **`catalog().length`**다 — `lib/questions.ts`의 개수가 아니다.
발행분이 있으면 둘은 **당연히 다르다.** 실제로 주간 점검이 "코드 103인데 API가 110,
DB에 잔재 7건"으로 올린 적이 있는데, 관리 화면에서 발행한 7건이었다(2026-08-18).

점검할 때의 올바른 기준:

- `questions`가 **103 미만**이면 진짜 이상 — 코드의 바닥이 무너진 것이다
- 103 이상은 정상. 초과분은 `/q` 페이지의 `/q/` 링크 수와 일치해야 한다
- 발행분 목록은 `/admin`에서 본다. 코드와 대조하려면 `catalog()`를 기준으로 한다

`questions.ts`는 **순수 데이터 모듈로 남긴다**(DB를 모른다). 병합은 `catalog.ts`에서만 한다 —
그래야 `questions.ts`를 읽는 자동화·검증 스크립트가 DB 없이 돌아간다.

### 충돌은 코드가 이긴다

`id`가 겹치면 기존 질문의 표에 붙고 `slug`이 겹치면 URL이 충돌한다.
관리 화면이 체크박스를 잠가 미리 막지만, DB를 직접 건드리는 경우까지 막으려면
`catalog()`에서도 걸러야 한다. **두 겹으로 막는다.**

### ⚠️ API 검증셋은 모듈 상수로 두면 안 된다

`/api/vote`·`/api/comments`의 `VALID`를 `new Set(QUESTIONS.map(...))`로 두면
**새로 발행한 안건에 투표·댓글이 404로 막힌다.** 요청마다 `validIds()`로 만든다.
`catalog()`는 60초 fetch 캐시라 `force-dynamic` 라우트에서도 왕복이 매번 생기지는 않는다.

### 404는 예외 — 코드만 본다

`app/not-found.tsx`는 `catalog()`를 부르지 않는다. 404는 **데이터 의존이 0이어야**
어떤 경로에서도 렌더된다(`notFound()` 경로의 렌더 보장이 약하다).
DB를 부르면 실패할 때 404가 빈 화면이 된다.

### 후보 적재 (`POST /api/ingest/draft`) — 별도 토큰인 이유

주간 자동 수집(클라우드 에이전트)이 부르는 유일한 엔드포인트다.
**`INGEST_TOKEN`은 `ADMIN_TOKEN`과 다른 값이어야 한다.**

클라우드 에이전트에는 `.env.local`이 없다. 그렇다고 루틴에 넣을 수 있는 값이 아무거나는
아니다 — 루틴 프롬프트는 **설정과 실행 로그에 그대로 남는다**.

| 후보 | 새면 |
|---|---|
| `SUPABASE_SERVICE_ROLE_KEY` | RLS 우회 전체 권한. **절대 안 된다** |
| `ADMIN_TOKEN` | 발행까지 가능. 안 된다 |
| **`INGEST_TOKEN`** | **미발행 후보 추가만.** 피해가 "대기함에 쓰레기가 쌓임"에 그친다 |

새는 것을 전제로 **권한을 좁혀서** 넣을 수 있는 값을 만든 것이다.

🔴 여기가 **자동 생성 콘텐츠가 들어오는 경계**다. 생산자를 믿지 않고 서버에서 검증한다 —
DB 제약만 믿으면 형식이 틀린 값이 500으로 튀고 원인을 찾기 어렵다.
id 형식·slug 금지문자·길이·topic·kind·선택지 동일 여부·**기존 질문과의 id/slug 중복**까지
막는다(9종 실측 확인). 거절 사유를 응답에 담아 자동화가 스스로 고칠 수 있게 한다.

### 관리 화면 (`/admin`)

`ADMIN_TOKEN` + httpOnly 쿠키. **Vercel 비밀번호 보호는 못 쓴다** —
Deployment Protection은 배포 단위라 `/admin`만 잠글 수 없고, 프로덕션을 보호하면
사이트 전체가 잠긴다. 게다가 Pro + 월 $150 애드온에 최소 30일 유지 조건이다.

- 토큰 미설정이면 **아무도 통과 못 한다**(미설정 배포에서 열려 있으면 최악)
- 상수 시간 비교 — `===`는 첫 불일치에서 멈춰 응답 시간으로 앞자리를 알아낼 수 있다
- `?k=`는 1회용 입구. 확인 즉시 쿠키로 바꾸고 리다이렉트해 주소창에서 치운다
  (쿼리스트링은 브라우저 기록·접근 로그·리퍼러에 남는다)
- 실패는 401이 아니라 **404**
- 🔴 **화면과 API가 같은 검사를 쓴다.** 두 벌이면 한쪽만 고쳐져 화면은 막혔는데
  API가 열리는 일이 생긴다
- 발행 취소는 **표를 지우지 않는다**. 화면에서 내릴 뿐이다

실측(검증 데이터 전량 삭제): 적재 → 발행 전 `/q` 미노출·상세 404 → 발행 →
`/q` 노출·상세 200·`/api/stats` 104 → **새 안건에 투표 200**.

## 색인 정책

`indexable(tally, commentCount)` = **표 20개 이상 그리고 댓글 1개 이상.**

**"또는"이 아니라 "그리고"다** — 표만 있고 댓글이 없으면 본문이 수치 두 줄뿐이라
여전히 빈 페이지다. 본문을 채우는 건 댓글이다.

- 미달이면 페이지가 `noindex, follow`를 낸다
- **사이트맵에도 통과한 질문만 넣는다.** 넣어 두고 noindex를 내면
  "이걸 보라" 한 뒤 "보지 마라"는 셈이라 크롤 예산만 태운다
- 홈·`/q`·`/best`·주제 허브·법적 고지는 항상 색인 허용
- 🔴 **닭-달걀처럼 보이지만 아니다.** 초기 트래픽은 커뮤니티 시딩이고, 시딩으로 표가 쌓이면
  색인이 자동으로 열린다. **SEO보다 시딩이 먼저다**

## 테마 — 🔴 **라이트 하나만** (2026-08-13 사용자 결정)

**종이는 항상 밝다.** 투표용지는 물리적 물건이니까. 그래서 다크 테마를 두지 않는다.

전에는 `prefers-color-scheme: dark`로 기표소(`--room`)가 어두워졌고, 그래서
**"어떤 컴퓨터에선 밝고 어떤 컴퓨터에선 어둡다"**가 됐다. 배경만 뒤집히면 같은 사이트가
두 얼굴이 된다. 스크린샷이 퍼지는 것이 이 사이트의 유통 경로이므로(브리프 원칙 4)
어디서 캡처해도 같은 모습이어야 브랜드가 쌓인다.

제거한 것: `@media (prefers-color-scheme: dark)` 토큰 블록 · `:root[data-theme='dark']` ·
다크용 흰 괘선 `body::before` 변형 · `themeColor`의 다크 항목.

- ⚠️ **`:root`의 `color-scheme: light`는 지우지 말 것.** OS가 다크여도 스크롤바·기본 폼
  컨트롤·자동완성 배경을 밝게 유지하는 선언이다. 없으면 밝은 페이지에 검은 스크롤바가 붙는다.
- ⚠️ `themeColor`는 단일값 `#e9e5dc`(기표소 배경과 동일) — 모바일 브라우저 상단 바가
  화면과 이어져 보이게.
- 다크를 다시 넣고 싶어지면 **위 이유를 먼저 반박할 것.** 색만 되살리면 되는 일이 아니다.

### 인주색(`--seal`)은 작은 글씨에 쓰지 않는다

라이트 기준으로도 `--seal` #c4302b는 `--room` #e9e5dc 위에서 **4.39:1**로 경계선이다
(작은 글씨 기준 4.5:1 미달). 중립 토큰과 비교:

| 색 | `--room` 위 대비 | 용도 |
|---|---|---|
| `--room-ink` #56514a | 6.25:1 ✅ | 방(헤더·푸터)의 본문 |
| `--room-faint` #877f75 | 3.14:1 | **의도적으로 흐린 보조 텍스트 전용** |
| `--seal` #c4302b | 4.39:1 (경계) | 큰 글씨·테두리·채운 배지의 **배경** |

그래서 헤더의 진행 표시("제 N호")는 `--seal`이 아니라 `--room-ink`를 쓴다.
`--room-faint`를 쓰는 "↓ 다음 안건"·푸터에는 **중요한 정보를 넣지 않는다.**

> 다크를 걷어내면서 이 값들도 다시 계산했다. 다크에서는 `--seal`이 2.93:1까지 떨어져
> 아예 못 쓰는 수준이었다 — 재사용 지식이라 통합 위키 `accessibility.md`에 남겼다.
